## Пункт 3. Заставка — так не получится, и вот почему (с фактами из кода клиента)

Ты просишь «вшить в сборку клиента, чтобы обновления не затирали». Проверил `app.asar` установленного
клиента (только чтением, ничего не менял):

1. **Переопределения снаружи для заставки нет.** Клиент грузит её жёстко:
   `loadingView.webContents.loadFile(path.join(__dirname, 'renderer', 'loading-overlay.html'))`.
2. **Подмена файла внутри `app.asar` невозможна в принципе.** `Info.plist` подписанного приложения
   содержит `ElectronAsarIntegrity` с SHA-256 архива (`com.extella.desktop`, hardened runtime).
   Заменишь файл — приложение не запустится, а не «переживёт до обновления».
3. **Мы не собираем клиент.** Сборка — у платформенной команды, версия сейчас 1.2.0.

**Но в том же коде есть готовый образец, и он твой ответ.** `toolbar.js` клиент ищет **сначала в
`userData`**, и только потом внутри себя:

```
let toolbarPath = path.join(app.getPath('userData'), 'toolbar.js');
if (!fs.existsSync(toolbarPath)) { toolbarPath = path.join(app.getAppPath(), 'packages/.../toolbar.js'); }
```

Именно поэтому наша витрина переживает обновления приложения.

**Поэтому правильная просьба к платформе — не «вшить файл», а сделать для
`renderer/loading-overlay.html` такое же переопределение из `userData`, как уже сделано для
`toolbar.js`.** Тогда твоя заставка ставится как витрина: положил файл — работает, обновление
приложения не трогает. Это ровно то, что ты просишь, только устойчиво и без патча подписанного
бандла. Оформлено в список к Тимуру (пункт D4 плана платформы).

Твои файлы (`HANDOFF/splash/loading-overlay.html` + `splash.mp4`) я не тронул — они ждут этого
переопределения. Локальная установка «до первого обновления» технически невозможна из-за пункта 2.
