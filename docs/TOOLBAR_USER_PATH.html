Рамка и канон

Extella Toolbar (приложение-витрина Extella) — строительная спецификация пользовательского пути. Кому: Анвар (со-основатель/CCO Extella.ai) и команды-исполнители. Пара к спецификациям Workspace-движка и Wizard в проекте «Разработка Extella». Документ — основа для стройки со стороны тулбара.

База (as-built). Тулбар — панель внутри Electron-приложения Extella. Приложение грузит UI из файла toolbar.js в userData (macOS: ~/Library/Application Support/extella-desktop/toolbar.js). Исходник — toolbar/public/plugins_manager.html (репо extella-toolbar-src), сборка node build.js → build/toolbar.js (инлайнит public/*.html + src/core/*.js). UI общается с устройством через мост на 8765 (skBridge → etb_run_expert/etb_run_agent и т.д.); мост исполняет эксперты/агенты на листенере (extella-listener, Python 3.12), листенер говорит с disnet.extella.ai. REST-ядро — api.extella.ai (заголовки X-Auth-Token / X-Profile-Id / X-Agent-Id). Токен и agent_id — в ~/extella_wizard/app/config.json.

Разделы витрины (вкладки): Рабочий стол · Витрина · Программы (включает влитые Pinokio-приложения) · Модели · Навыки · Инструменты · Знания · Workspace · Агенты · Сервисы · Профи. Режимы «Для всех» / «Для профи».

Легенда статусов: есть — работает сегодня, проверено; частично — работает не целиком или требует сверки; построить — отсутствует. Рабочие имена новых операций/файлов — предложение, в текущем коде их нет.

Инварианты (канон, нарушать нельзя):

  • Всё ставится по кнопке, без LLM-токенов. Установка любой карточки витрины — детерминированные эксперты/рецепты/пакеты, не агент. Токены тратятся только при РАБОТЕ агентных способностей (Композитор, штурм) — это использование, не установка.
  • Клиентские агенты — платформенный Qwen 3.7. BYOK/gpt-4o запрещён; платный Claude-дефолт (agent_extella_default) клиентам не ставится — подмена на agent_extella_alibaba_default.
  • Приложения/файлы человека не трогаются без его действия. Удаление приложения и воркспейса — по подтверждению; удаление воркспейса сносит только рабочую среду, файлы на диске целы.
  • Показываем только совместимое с машиной человека. Тулбар определяет ОС и прячет несовместимое (напр. NVIDIA-приложения на Mac).
  • Тулбар v6 не патчим напрямую — только через исходник и пересборку; прод-плагины и реестр не ломаем.
  • Секреты (токен, PIN-хеш) в логи и чаты не печатаются.

2. Таксономия контента витрины

2.1. Принципы

  • Единая обещание витрины: «то, что мы рекламируем и совместимо с машиной человека — ставится по кнопке, детерминированно, без токенов». Каждый тип имеет свой детерминированный установщик.
  • Каталоги — в KV, шардированы (_mkt_models, _mkt_mcp, _mkt_apps, _mkt_programs, _mkt_skills_catalog, _mkt_cli_catalog, composer:catalog). Первый шард несёт shards:N; UI склеивает через _loadSharded. Глобально-засеянные ключи читать с global:true.
  • Витрина = директория/реклама GitHub-репозиториев (для приложений/программ): мы не распространяем код приложений, а рекламируем репо; лицензия репо — забота пользователя. Установщик клонирует и исполняет рецепт на его машине.
  • Честность про совместимость: «совместимо по рецепту» ≠ «проверено вживую». Метка verified ставится только после реального прогона (deep-verify).

2.3. Установка «в один клик по ссылке» (cmdInstall)

Верхняя строка витрины: «Вставь ссылку, установим в один клик: программа, модель, навык, CLI». Механизм: детект типа по URL/тексту → маршрутизация в нужный установщик. GitHub-репо → приложение/программа; HF-ссылка → модель; иначе — Строитель (агент) подбирает. Часть детекта детерминирована, часть уходит агенту (best-effort).

Осталось: пакетно сконвертировать 178, поле xrecipe в карточке → тулбар выбирает recipe_x vs app_install. частично — доказано на 1, каталог не сконвертирован.
