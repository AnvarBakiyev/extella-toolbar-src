## Результат

Evolution Console больше не скрывает разницу между числом карточек на
устройстве и числом подтверждённых автоматизаций. Сканер отдаёт безопасный
инвентарь всех карточек, провайдер классифицирует каждую карточку по
каноническому доказательству, а экран показывает сверку до списка
автоматизаций.

На живом локальном наборе результат такой:

- найдено карточек: `16`;
- подтверждено бизнес-автоматизаций: `3`;
- системных поверхностей Extella: `4`;
- требуют решения владельца: `9`.

Первые три остаются основным парком: `extella_1c_agent`,
`extella_contract_agent`, `extella_travel_agency`. Все 16 строк доступны в
раскрываемом блоке `Технические данные`; ничего не исчезает молча.

## Правило классификации

Карточка становится бизнес-автоматизацией только при одном из трёх
доказательств:

1. `AUTOMATION_PASSPORT`: `automation.automation_id` существует и совпадает с
   `manifest.id`.
2. `PROCESS_MANIFEST`: карточка объявлена процессом через
   `category=automations` + `type=process` либо схему
   `extella-process-pack-v1` (`schemaVersion` или `schema_version`).
3. `REVIEWED_MIGRATION`: временная закрытая миграция только для трёх уже
   проверенных автоматизаций. Добавлять новые ID в этот список запрещено.

`system: true` классифицирует карточку как `SYSTEM_SURFACE`. Остальные карточки
получают `UNCLASSIFIED / CLASSIFICATION_MISSING` и видны пользователю, но не
выдаются за автоматизации.

Такой порядок позволяет довести парк до семи и дальше без новых whitelist в
Console: продукт приезжает с паспортом автоматизации — Console подхватывает его
автоматически.

## Очередь развития после этого среза

Задачи Console и Evolution Lab идут в таком порядке:

1. **Парк 7+ без whitelist.** Принять четыре паспорта от владельцев, убрать
   `CLASSIFICATION_MISSING` у подтверждённых продуктов и добавить release-gate:
   бизнес-карточка без Automation Passport не выпускается.
2. **Честное состояние каждой автоматизации.** Для семи карточек различать
   `WORKING / NOT_RUNNING / STATE_UNAVAILABLE`, показывать последний запуск,
   результат, локализованную ошибку и блокировать действие при отсутствии
   состояния. Расписания входят в тот же dead-reference расчёт.
3. **Карточка автоматизации как рабочее место.** На первом уровне оставить
   один статус, одно главное замечание и один следующий шаг; состав внутренних
   агентов, MCP и технические доказательства держать в раскрытии. Переход к
   одному агенту выполняется только в существующий Agent Cabinet.
4. **Вход изменений из Agent Cabinet.** Принять эскалацию с точным агентом,
   Automation ID, baseline hash и ссылками на доказательства; без доказанного
   change context Evolution Lab не открывать.
5. **Evolution Lab.** Сравнение baseline/candidate, влияние через Shared Genes,
   тестовый прогон без записи в production, результат с точным snapshot и
   понятным «что изменится».
6. **Одиночные trusted actions.** Включение, остановка, обновление и откат
   разрешать только через routed action: три предзаписных гейта ссылками,
   host-side read-back, идемпотентность и честный
   `PUBLISH_OUTCOME_UNKNOWN`.
7. **Массовые операции.** Только после зрелости одиночного пути: точный список
   целей, preview воздействия, staging, перечитывание каждой цели, отдельные
   Evolution Receipts и откат на экране.
8. **Эксплуатация.** История запусков и изменений, уведомления о новых
   проблемах, экспорт доказательств и продуктовая телеметрия понятности экрана;
   технические enum не выносить в основной пользовательский слой.

Внешние входы интегратора нужны в пунктах 1–2 (паспорта, доставка сканера и
state-контракты владельцев) и перед production-release пунктов 6–7 (host routed
actions и официальный deploy). Console отвечает за read model, интерфейс,
Evolution Lab, гейты вызова и тесты поверхности.
