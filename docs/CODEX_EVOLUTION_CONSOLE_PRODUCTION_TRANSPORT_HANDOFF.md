# Handoff: production-транспорт Evolution Console

Дата: 05.08.2026

Ветка: `codex/evolution-console-production-transport`

База: `origin/main@c474589`

Версия карточки: `0.13.0`

## Результат

Evolution Console перенесена на свежий `origin/main` и использует один
канонический путь определения устройства. Чтение реестра больше не зависит от
случайного fallback-устройства, выдерживает реальный двухслойный ответ моста и
не обрывается клиентским таймаутом раньше эксперта.

Этот срез не добавляет изменяющих действий. Console остаётся read-only и
fail-closed: если точное устройство или честный снимок не получены, действия не
разрешаются.

## Что изменено

1. `router` один раз разрешает точный `deviceId` через host-механику из свежего
   `main` и передаёт его провайдеру реестра.
2. Явная ошибка host-resolution больше не может незаметно переключить чтение на
   другое устройство из `window.etbDeviceId`.
3. Вызов сканера закреплён одновременно полями `target` и `targets` за одним
   точным устройством.
4. Клиентский таймаут `180000 ms` передаётся только транспортному `_post` и не
   попадает в тело API-запроса. Серверный контракт эксперта не подменяется
   старым `timeout: 20`.
5. Ответ сканера разбирается в четырёх ограниченных слоях: прямой контракт,
   `result`, `res.result` и `output`. Повреждённый JSON становится явной ошибкой,
   а не пустым парком.
6. Если `etb_init` не пришёл за 15 секунд, экран прекращает бесконечное ожидание
   и показывает локализованную причину и следующий шаг.
7. В интерфейсе видна версия `0.13.0`, поэтому устаревший кэш можно отличить от
   дефекта продукта.
8. Тексты поверхности приведены к строгому бренд-гейту; цвета остаются точными
   токенами действующего дизайн-канона Эллы и помечены поддерживаемым
   `canon-ok` с причиной расхождения старой машинной палитры.

## Совместимость со свежим main

Ветка создана от `origin/main@c474589`, а четыре ранее проверенных коммита
Evolution Console перенесены поверх этой базы. Новая host-логика поиска
устройства из `main` не продублирована и не переписана.

Два теста старого feature-среза были приведены к уже существующему в свежем
`main` асинхронному контракту `runExpertAsync`; продуктовый код MCP при этом не
менялся.

## Что требуется от интегратора

1. Проверить и слить ветку только поверх актуального `origin/main`.
2. Выполнить официальный build/install из чистого `main`; feature-worktree не
   является источником production-деплоя.
3. На целевом аккаунте подтвердить, что установлен эксперт
   `_etb_evolution_registry_scan_v1` и Console получает ответ с того же точного
   `deviceId`, который показывает host.
4. После релиза открыть карточку и проверить видимую версию `0.13.0`, затем
   сверить счётчики полного инвентаря с живым ответом сканера.
5. Продолжить внешний вход по паспортам автоматизаций и state-контрактам: без
   них Console честно показывает `требует классификации` или `состояние
   неизвестно`, а не придумывает рабочее состояние.

## Следующий продуктовый срез

После приёмки транспорта Console берёт на себя:

1. рабочую карточку одной автоматизации: один статус, главное замечание и один
   следующий шаг;
2. честное состояние и история последнего запуска без смешения с доступностью в
   каталоге;
3. приём эскалации из существующего Agent Cabinet в Evolution Lab;
4. одиночный trusted action с тремя ссылками на доказательства, host-side
   read-back, идемпотентностью и `PUBLISH_OUTCOME_UNKNOWN`;
5. массовые операции только после доказанной зрелости одиночного пути.

Входы интегратора для этих пунктов: паспорта и state-контракты владельцев,
routed trusted action на host и официальный production-release. Console не
переписывает внутреннюю логику агентов.

## Rollback

Откатить merge-коммит и повторить официальный build/install из чистого `main`.
Срез не изменяет Agent Genome, Shared Genes, реестр установок или состояние
автоматизаций.
